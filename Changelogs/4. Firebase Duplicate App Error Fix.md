## 2. Root Cause Analysis

### A. Android Native Pre-initialization
In `android/app/build.gradle.kts`:
```kotlin
plugins {
    id("com.android.application")
    id("dev.flutter.flutter-gradle-plugin")
    id("com.google.gms.google-services")
}
```
The Google Services Gradle plugin parses `android/app/google-services.json` and injects `com.google.firebase.provider.FirebaseInitProvider` into the Android manifest. At app launch, before Flutter or Dart runs, Android's `FirebaseInitProvider` automatically initializes the native `FirebaseApp` instance named `[DEFAULT]` using values from `google-services.json`:
- `apiKey`: `AIzaSyAVr2RF_W3aAEz0rCy7q-V1J78cFhuwQL8`
- `projectId`: `eclassify-3800d`
- `storageBucket`: `eclassify-3800d.firebasestorage.app`

### B. Empty Placeholder Values in `firebase_options.dart`
In `lib/firebase_options.dart`, `DefaultFirebaseOptions.android` had empty strings:
```dart
static const FirebaseOptions android = FirebaseOptions(
  apiKey: '',
  appId: '',
  messagingSenderId: '',
  projectId: '',
  storageBucket: '',
);
```

### C. Options Conflict in `firebase_core_platform_interface`
In `lib/main.dart`, `_initializeFirebase()` called:
```dart
await Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform);
```
In Flutter's `method_channel_firebase.dart` (lines 124–134):
```dart
if (defaultApp != null && _options != null) {
  if (_options.apiKey != defaultApp.options.apiKey ||
      (_options.databaseURL != null &&
          _options.databaseURL != defaultApp.options.databaseURL) ||
      (_options.storageBucket != null &&
          _options.storageBucket != defaultApp.options.storageBucket)) {
    // Options are different; throw.
    throw duplicateApp(defaultFirebaseAppName); // Line 131!
  }
  // Options are roughly the same; so we'll return the existing app.
}
```
Because `defaultApp.options.apiKey` contained the real API key while `_options.apiKey` was empty (`''`), Flutter recognized them as conflicting Firebase app configurations targeting the same `[DEFAULT]` app name and threw `[core/duplicate-app]`.

### D. Hot Reload & Hot Restart Handling
Additionally, calling `Firebase.initializeApp()` without verifying `Firebase.apps.isEmpty` or handling `duplicate-app` would cause crashes on subsequent re-runs or hot restarts where the native Android process keeps the `FirebaseApp` instance active in memory.

## 3. Solution Implemented

### Step 1: Updated `lib/firebase_options.dart`
Populated `DefaultFirebaseOptions.android` with the actual project credentials from `android/app/google-services.json`:

```dart
  static const FirebaseOptions android = FirebaseOptions(
    apiKey: 'AIzaSyAVr2RF_W3aAEz0rCy7q-V1J78cFhuwQL8',
    appId: '1:845338884833:android:8d369774dafacc03c0d5a0',
    messagingSenderId: '845338884833',
    projectId: 'eclassify-3800d',
    storageBucket: 'eclassify-3800d.firebasestorage.app',
  );
```
*Result:* `_options.apiKey == defaultApp.options.apiKey` now evaluates to `true`. Instead of throwing `duplicateApp`, Flutter reuses and returns the existing native app instance.

### Step 2: Added Lifecycle and Hot-Restart Guards in `lib/main.dart`
Updated `_initializeFirebase()` with an `apps.isEmpty` check and caught `duplicate-app` exceptions defensively:

```dart
/// Initializes Firebase with appropriate options
Future<void> _initializeFirebase() async {
  try {
    if (Firebase.apps.isEmpty) {
      await Firebase.initializeApp(
        options: DefaultFirebaseOptions.currentPlatform,
      );
    }
  } catch (e) {
    if (e is! FirebaseException || e.code != 'duplicate-app') {
      rethrow;
    }
  }

  await FirebaseAppCheck.instance.activate(
    providerApple: kDebugMode ? AppleDebugProvider() : AppleAppAttestProvider(),
    providerAndroid: kDebugMode
        ? AndroidDebugProvider()
        : AndroidPlayIntegrityProvider(),
  );
}
```
